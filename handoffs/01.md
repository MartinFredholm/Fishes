# Handoff 01: Front stiffness

## Built
In `updateSharkBody`, after the spine is placed on the nose path and before the zero-amplitude early return, `stiffenFront` rebuilds the front of the spine. The anchor is the first node with s ≥ `front_stiff_s`: node 9 (s = 0.391) with 24 nodes and 0.35. Nodes from the anchor back are untouched.

Going from the anchor toward the nose, each node i adds the bend it withholds, κ_i · L/23 · (1 − smoothstep(s_i / `front_stiff_s`)), to a running total. Node i−1 is then placed at node i plus the nose path's own chord (on-path node i−1 minus on-path node i), rotated by that total. So each front node bends by the path's own chord turn minus its withheld bend. On a steady circle that is exactly κ·L/23·smoothstep, the issue's construction. The smoothstep is clamped at 1, so the anchor bends like the path, with no kink.

The body line is unchanged.

Measured, zero amplitude:
- Head lag behind `kin.heading`: 0.427 rad at cruise (target 0.42) and 0.847 rad in the tightest turn (target 0.84).
- The drawn nose sits 13.0 cm outside `kin.pos` at cruise (R = 1.25 m) and 25.4 cm in the tightest turn (R = 0.625 m).
- Swimming straight, node 0 stays within 1.5e-6 m of `kin.pos`.

## Interfaces provided
- `BodyParams::front_stiff_s` (float, fraction of L). Set to 0.35 in `fishes.cpp` (`SHARK_BODY`) and in `tests/test_support.h` (`bodyParams`).
- `std::vector<float> pathCurvatureAtNodes(const std::vector<PathPoint> &path, const BodyParams &params)` in `shark_body.cpp`, anonymous namespace. It returns one value per spine node, in 1/m, signed like `kin.r` (positive curves screen-left). It is evaluated at arc s·L behind the nose. Method: the phi-signed turn between the chords (arc − Δ → arc) and (arc → arc + Δ), divided by Δ, with Δ = L/(N−1). That is exact on a circle. The window centre is clamped to [path.front().arc + Δ, nose_arc − Δ], so node 0 reads the curvature at s = 1/23 and the tail tip at about s = 22/23. Issue 02 can call it directly; `updateSharkBody` currently computes it once per update, inline in the `stiffenFront` call.
- Helpers in the same namespace: `pointAtAnyArc` (binary search, clamps at both ends), `turnAngle(a, b)` (phi-signed angle from a to b), `segmentLength(params)`, `smoothstep(t)` (clamps t to [0, 1]).

## Deviations
- The stiff length is 0.35, not the 0.25 first planned. The user asked for a stiffer front, and the spec, glossary and issue 01 were updated to match. The R3 targets are now κ·L·0.35/2: 0.42 and 0.84 rad.
- ⚠ The front is built by rotating the nose path's own chords, not by chaining segments of L/23 from the anchor's direction as the issue describes. Reason: at 0.35 the chain multiplied the anchor chord's float rounding by the 1.17 m front, and node 0 ended up 1.2–1.5e-5 m off `kin.pos` when swimming straight, failing R4 (1e-5). This was confirmed by zeroing the bends: still 1.4e-5. On a steady circle the two methods give the same spine. Consequence: at zero amplitude, front segments have the path's chord length, up to 0.2 % short in the tightest turn, like the rest of the spine (R5 allows this). With amplitude, the length pass resets them to L/23.
- The existing test "zero amplitude, circular path: nodes on the circle at s·L" is now restricted to s ≥ 0.35, like the R1 tests. The user approved this, and the spec now lists it.
- "spine node 0 is the nose every frame" now swims straight at phi = 0.7 instead of phi = 0. With phi = 0 the check would be trivially exact.

## Not verified
- How it looks in the running app (head stillness). The user judges that by eye.
- R7 smoothness of the curvature on a straight path with uneven dt. It is not tested here; it belongs to issue 02.
- Whether the 25 cm offset of the drawn nose in the tightest turn looks right. Eating and targeting still measure from `kin.pos`.
