# Handoff 04: Shark avoidance

## Built
- `shark_avoidance.h` / `shark_avoidance.cpp`: the pure function `avoidSharks` and its constants. CMake library `shark_avoidance` links `shark_body` (for `nearestPointOnBodyLine`) and `motion` (for `integrate` and the world size) publicly. Like those two, it does not link raylib. Both `fishes` and `shark_body_tests` link it.
- Prediction: from the shark's current kinematics, `integrate` is stepped at `SHARK_AVOID_DT` = 1/30 s for round(horizon / dt) = 75 steps, with the commands held constant. Step k is at t = k·dt. The current state (t = 0) is not scored, since it is the same for every candidate.
- Other sharks' body lines move rigidly by heading·v·t (R17). The code moves the predicted nose by −heading·v·t into the frame of the unshifted line instead of copying the line. The result is the same.
- Shark clearance, wall clearance and score follow R18. Wall clearance is min(x, W − x, y, H − y) − `params.wall_clearance`, from the nose.
- Choice (R19): if the commanded candidate's shark clearance is ≥ `SHARK_AVOID_MARGIN`, the commands come back unchanged. Otherwise left and right are compared. A difference under `CLEARANCE_TIE` goes to the side of `self.r` (r ≥ 0 → left, as the wall safety filter does). Straight is returned only if its score is strictly higher than the chosen side's.
- `fishes.cpp`: `otherSharks(i, sharks_old)` builds the `others` list from the previous frame's sharks, without shark i. In the shark loop, `avoidSharks` runs between `getCommands` and the unchanged `safetyFilter` (R15).
- `tests/shark_avoidance_tests.cpp`, suite "shark avoidance": the seven spec scenarios, as 9 test cases.

## Interfaces provided
`shark_avoidance.h`:
- `struct OtherShark { Kinematics kin; std::vector<Vector2> body_line; };`: as planned.
- `Commands avoidSharks(const Kinematics &self, Commands commanded, const std::vector<OtherShark> &others, const MotionParams &params);`: as planned.
- `SHARK_AVOID_HORIZON` = 2.5 s, `SHARK_AVOID_MARGIN` = 0.2 m, `SHARK_CONTACT_DISTANCE` = 0.36 m. Issue 05 retunes the first two here.
- ⚠ Also `SHARK_AVOID_DT` = 1/30 s, the fixed prediction step from R16. It is a named constant so it is not a magic value. It is not a tuning value.

## Not verified
- I did not check by eye that sharks avoid each other in the running program. I only ran `fishes` for 5 s to confirm it starts and runs.
- I did not measure the contact rate. That is issue 05.
- Cost: 4 candidates × 75 steps × (N − 1) others, each a 4-segment nearest-point scan, per shark per frame. At N = 2 this is trivial. At N = 10 it is about 27 000 segment tests per frame, which I did not profile.
- Several tests passed on their first run, because the code for an earlier item already covered them. To show they can fail, I mutated the code temporarily and restored it each time:
  - Picking the worst option fails the left/right tests.
  - Holding the other sharks still fails the crossing test and the head-on test.
  - A contact distance of 0.5 m fails the side-by-side test.
  - Dropping wall clearance from the score fails the wall-trap test.
- The tie-rule test places the other shark 2 mm to the right, so left scores about 2.6 mm higher than right, which is inside the 10 mm tie. I measured these values with a scratch program. A retune of the horizon in issue 05 could move them, but the gap would stay far below 10 mm.
